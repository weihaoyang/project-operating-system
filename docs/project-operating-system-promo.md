# 把 Codex 变成真正的项目操作系统

大项目最怕的，从来不是代码难写。

真正让项目失控的是：做到一半以后，上下文断了；新代理重复扫描；多个代理同时改同一个文件；测试越跑越多，却没有证明新的东西；遇到问题只能重新搜索；代码越来越多，架构越来越复杂，却没人能准确说出项目到底完成了什么。

`project-operating-system` 是一套为 Codex 打造的跨项目工程工作流。它把 Codex 从一次性代码生成器，升级为能够研究、规划、接管、恢复、验证并持续交付大型项目的项目操作系统。

## 项目做到一半，也能无缝接管

不需要重新解释背景，也不会把旧项目当成空项目。

运行一次接管流程，它会读取 Git 分支、最近提交、未提交改动、依赖清单、测试入口、checkpoint、运行记录和现有项目文档，生成紧凑的项目 inventory，并把当前状态区分为：

```text
已确认 · 已实现但未验证 · 部分完成 · 被阻塞 · 未知
```

它保留已有代码、历史和决策，只围绕当前最高价值缺口继续推进，不从头扫描，不重跑整套测试，不凭感觉宣布完成。

## 开始开发之前，先做正确的选择

当你说“我要开发一个新的系统”，它不会立刻创建文件、堆技术栈、输出代码。

它会先调研 GitHub 同类开源项目，检查真实代码、架构、依赖、许可证、活跃度、测试、issue 和常见坑点，最后给出：

- 技术选型；
- 系统架构；
- MVP 边界；
- 开发顺序；
- 风险与开放决策。

等你确认之后，才进入实现阶段。让项目从第一天就少走弯路，而不是先写一堆代码再补架构。

## 第一性原理，奥卡姆剃刀

每次增加代码、抽象、代理、测试或门禁之前，先回答：

```text
用户真正要的结果是什么？
必须保持的不变量是什么？
最短的因果链是什么？
最小的可证伪检查是什么？
```

它不鼓励为了“看起来专业”而增加中间层、状态、服务和文档。每一个复杂度都必须对应一个真实风险，每一个流程都必须产生可验证的价值。

## 防止过度防御性编程

它不会鼓励：

- 到处添加没有业务意义的空值判断；
- 每一层重复校验同一个条件；
- 用静默 fallback 掩盖真实错误；
- 用吞异常换取表面稳定；
- 为尚不存在的需求提前设计复杂抽象；
- 用大量分支替代清晰的数据契约。

每一段防御逻辑都必须回答：

> 它具体防止什么真实故障？触发之后应该修复、失败，还是明确降级？

真正的安全边界会保留，没有实际价值的防御代码会被删除。系统不会把未知状态伪装成成功，也不会把所有代码都包进无意义的保险层。

## 防止过度测试

它不把“测试越多”当成“质量越高”，而是按变更风险选择最小充分验证：

```text
文档修改       → diff 检查
单函数修改     → 语法检查 + 目标单测
API/数据库修改 → 两侧测试 + 一个 smoke
训练/数据任务  → smoke + 真实数量/范围/hash
生产发布       → 关键集成测试 + 回滚验证
```

完整测试、长矩阵、全量构建，只在高风险、发布或确实需要时执行。每个额外门禁都必须说明它捕获的具体失败；没有明确失败模式的检查，默认不增加。已经验证且依赖、输入和环境没有变化的证据，直接复用。

## 多代理协作，不再互相覆盖

每个任务都有：

```text
objective key  → 防止重复解决同一个问题
ownership key  → 防止修改重叠文件
worker budget  → 防止无限并行
task contract  → 明确范围、验收和停止条件
```

派发代理之前，会读取 Codex 线程快照并和项目 active registry 对账；相同目标直接复用，不重复创建。涉及 schema、migration、公共 API、lockfile 和核心配置时，自动收敛为单一 owner。

线程工具可用时保存 `thread_id` 和 `host_id`；工具不可用时进入降级模式：最多一个 worker，禁止并发写入，不假装同步成功。

## 困难问题不会再丢

遇到阻塞时遵循：

```text
最小复现
→ 查项目历史
→ 查官方文档和 GitHub issue
→ 验证最小修复
→ 写入本地知识库
```

知识库记录问题、环境、根因可信度、解决方案、验证结果、来源、验证时间和复核时间。下一次遇到类似问题，先搜索已有知识，不再重复消耗 token。

## 长任务可恢复，部分完成不冒充完成

适用于数据下载、GPU 训练、回测、批量迁移、后台构建和生产任务：

```text
环境预检
→ 单实例锁
→ heartbeat
→ checkpoint
→ 分批执行
→ status
→ resume
```

执行器超时、网络中断或窗口关闭后，可以从真实 checkpoint 恢复，不会重复启动第二个任务，也不会把半成品、mock、placeholder 或空结果当作完成。

## 证据驱动的项目收口

它严格区分：

```text
implemented
tested
verified
promoted
production_ready
```

重要结论必须绑定命令、结果、artifact、checkpoint 或 hash。“文件存在”不等于“功能完成”，“测试通过”也不等于“系统已经可以上线”。

## 小项目轻量，大项目治理

根据风险自动选择工作流档位：

```text
lite       小脚本、简单工具、轻量修改
standard   常规网站、应用、研究项目
high-risk  交易、支付、医疗、生产、训练、数据完整性任务
```

项目越简单，流程越轻；风险越高，证据越完整。不会为了“最佳实践”给一个小脚本生成一整套企业级文档。

## 它真正带来的变化

```text
更少的重复扫描
更少的无效测试
更少的防御性代码
更少的代理冲突
更少的上下文浪费
更清晰的架构边界
更可靠的项目恢复
更完整的证据链
```

一句话介绍：

> `project-operating-system`：让 Codex 既不会漏掉真正的风险，也不会为了防风险把项目做复杂。

最终目标不是让项目做得更多，而是用更少的代码、更少的测试、更少的代理和更少的 token，把真正重要的事情做对、做稳、做完。
